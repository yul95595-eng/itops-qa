# 评测体系使用说明

> **一句话**：把「跑一次出个分数」变成「改一个参数 → 跑一次 → 和上次比 → 看哪几道题退化了」。
>
> **定位要说清**：这是**单项目内的评测闭环**，不是评测中台。中台要满足「多个接入方 + 指标口径收到一处 + CI 卡合入」，这里只做到第二层。

---

## 一、目录结构

```
data/eval/
├── datasets/
│   ├── v1.jsonl               # 质量集 40 题（冻结，唯一真相）
│   ├── v1.retrieval.jsonl     # 检索集 32 题
│   └── manifest.json          # 版本登记 + sha256
├── independent_set.py         # 源头（已导出，改它要重新导出并升版本号）
└── retrieval_set.py

logs/eval_runs/
└── 20261118_2015_quality_baseline.json   # 每次结果一个文件
```

**为什么把 `.py` 里的题导出成 `.jsonl`**：题目写在代码里，加一道题要改代码、没法 diff、不会 Python 的人加不了，而且**没人知道这次的 40 题和上次的是不是同一批**。导出后每次结果都带 `dataset_sha256`，对比时校验。

## 二、三条命令

### 1. 导出测试集（只在改题时用）

```bash
python scripts/export_dataset.py            # 首次导出 v1
python scripts/export_dataset.py --check    # 校验 .py 和 .jsonl 是否仍然一致
python scripts/export_dataset.py --version v2   # 改过题，导新版本
```

**`--check` 是护栏**：如果有人改了 `.py` 却没重新导出，评测跑的仍是旧题，结论就是假的。这条命令会直接报「有漂移」。

### 2. 跑一次

```bash
python scripts/eval_all.py --suite quality --tag baseline
python scripts/eval_all.py --suite retrieval --tag rerank_off
python scripts/eval_all.py --suite both --tag v2_release
python scripts/eval_all.py --suite quality --limit 5 --tag smoke    # 冒烟，5 题
python scripts/eval_all.py --list                                   # 看历史
```

结果写到 `logs/eval_runs/<时间>_<suite>_<tag>.json`，里面包含：

| 字段 | 内容 |
|---|---|
| `dataset_version` / `dataset_sha256` | 用的哪批题、内容指纹 |
| `config` | `RETRIEVAL_K` / `CANDIDATE_M` / 阈值 / 模型名等参数快照 |
| `git_commit` | 哪次提交跑的 |
| `metrics` | 答对率、拒答准确率、编造数、误拒率、延迟 P50/P95、异常数 |
| `cases` | 逐题明细：`layer`、`ok`、判定理由、耗时、答案前 200 字 |

**两个 suite 的区别**：

| suite | 走什么 | 测什么 | 单题耗时 |
|---|---|---|---|
| `quality` | 完整 pipeline（含 LLM 生成） | 端到端答对率、拒答能力 | 20~35 秒 |
| `retrieval` | 只走检索 + 重排 | 文件级 Recall@m / MRR | 13~16 秒 |

### 3. 对比

```bash
python scripts/eval_compare.py --base baseline --cand latest
python scripts/eval_compare.py --base <旧.json> --cand <新.json> --md logs/compare.md
python scripts/eval_compare.py --base baseline --cand latest --max-drop 2
```

输出三段：**指标变化表** → **逐题翻转**（哪几题从对变错、哪几题从错变对）→ **门槛判定**。

`--max-drop 2` 表示主指标下降超过 2pp 就退出码 1，可以直接挂到 git hook 或 CI 上。

## 三、典型的用法：改一个参数，判断要不要留

```bash
# 1) 已有基线
python scripts/eval_all.py --suite retrieval --tag baseline
#    假设 Recall@8 = 90.6%

# 2) 改参数（比如关掉 reranker）
python scripts/eval_all.py --suite retrieval --tag rerank_off --note "CANDIDATE_M 保持 8，跳过重排"

# 3) 对比
python scripts/eval_compare.py --base baseline --cand rerank_off --max-drop 2
```

预期看到类似：

```
指标                    基线        候选        变化
Recall@8             90.60%      87.50%     ↓3.10pp  ⚠️
延迟 P50             15569ms       220ms  ↓15349ms  ✅

逐题差异（共比对 32 题）
  退化 2 题：
    ❌ R07   两个网卡都有网，流量走哪个    rank 2 → 未命中
```

**判断逻辑**：3.1pp 的召回换 15 秒延迟，值不值取决于场景。**但这个判断现在有数字支撑了，不是拍脑袋。**

## 四、三道防错设计（都是实测踩出来的）

| 机制 | 防的是什么 | 触发时会怎样 |
|---|---|---|
| **`dataset_sha256` 校验** | 换了题却拿旧报告对比，"提升 2 个点"是假的 | 对比时打⚠️告警并明确写出「数据集内容不同」 |
| **suite 不同直接拒绝** | 把检索结果和端到端结果放一起比，算出一堆「—」看着像能比 | 报错退出，不输出无意义的表 |
| **tag 歧义打回** | `--base smoke` 匹配到两份（质量+检索各一），静默取最后一个会让**基准选错** | 列出所有候选的 run_id，要求指定具体哪个 |

第三条是实测时真撞上的：`--base smoke` 取到的是检索那份，对比表里一堆「—」，如果不细看就会以为是"没数据"而不是"选错了基准"。

## 五、首份全量基线（40 题，rerank 开，k=20 / m=8）

```
答对率        38/40 = 95.0%
拒答准确率    8/8  = 100.0%   (架构拦截 8 / 模型自觉 0 / 编造 0)
误拒率        0/32 = 0.0%
延迟          P50 514ms   P95 44.9s
总耗时        646s
```

**P50 只有半秒而 P95 有 45 秒**，这是正常的，不是异常：40 题里 6 道走 FAQ、8 道走错误码、1 道走闲聊、7 道被域判定拦下，这些都是毫秒级；只有 18 道真进 RAG 的才吃 20~45 秒的重排 + 生成。**看延迟必须看分位数，看平均值会得到 15.8 秒这种两头不靠的数。**

### 抓到的两个真实缺陷

**A04 · 打印机 → 回了 U 盘（实体错配）**

```
[4/6] 打印机按了没反应，纸也不动    layer=faq
答案：换 USB 口；设备管理器查看是否识别；换电脑测试区分 U 盘和接口问题
日志：BM25 命中 raw=7.53 margin=0.36 -> U 盘插上没反应
```

「打印机按了没反应」和「U 盘插上没反应」共享「没反应」，BM25 是纯词面匹配，`raw=7.53 ≥ 5.0`、`margin=0.36 ≥ 0.3` 双判据都过了，于是直接短路返回。

**这是回归，不是一直存在的缺陷**：`logs/independent_report.md` 历史记录是 39/40（只错 B07），A04 当时是**对的**。也就是说某次改动让 FAQ 层开始错误命中这条，而**没有任何人发现**——直到这次跑全量基线。

**B07 · 杀毒 → 回了闪退（错别字导致实词丢失）**

```
杀度软件把程序删了    layer=faq
答案：查看事件查看器错误日志；更新软件和驱动；兼容模式运行；仍闪退联系 IT
```

「杀度」是「杀毒」的错字，jieba 切不出正确词，于是 query 里只剩「程序」这个通用词在起作用，恰好匹配到「软件闪退」那条。

### 两个缺陷的根因不同，修法也不同

| | A04 | B07 |
|---|---|---|
| 根因 | **实体不同但共享功能描述词**（"没反应"） | **错别字使关键实体词丢失**，只剩通用词 |
| 修法 | 命中后做**实体一致性检查**：query 里出现的设备名（打印机/U 盘/键盘/显示器…）如果与 FAQ 原题的设备名完全不重叠，就不短路，降级走 RAG | 要求**至少 2 个实词重叠**，或对错别字做同音纠正后再匹配 |
| 为什么不能只调 margin | 调高 margin 会误杀真实的短问命中 | 同上 |

**这件事本身就是评测闭环的价值证明**：这两个缺陷在之前所有手工测试里都没被发现——手工测试只会问「打印机坏了怎么办」这种标准问法，不会恰好撞上「按了没反应」这种共享功能词的表达。

### 顺带修掉的一个口径 bug

首版全量跑出「拒答 7/8、编造 1」，查下来是**评测自己的判定函数不认识新层**：`_classify_refusal` 只把 `fallback` 算作架构拦截，而后来加的 `out_of_domain`（域外判定）和 `chitchat`（闲聊）同样是"进 RAG 之前就被挡住"，却被分别错记成"模型自觉"和"编造"（引导语里没有拒答词，于是落到 halluc）。

修正后 `8/8 + 编造 0`，对比结果：

```
拒答准确率   87.50% → 100.00%   ↑12.50pp
编造数            1 → 0         ↓1
逐题改善：E01（今天天气怎么样）
```

**这就是为什么判定逻辑只能有一份**：口径一改，历史数字全部要重算，多一份拷贝就多一处对不上的风险。

## 六、还差什么才算"评测中台"

诚实盘点：

| 中台该有的 | 现在有没有 |
|---|---|
| 测试集版本化 | ✅ 有了（manifest + sha256） |
| 指标口径统一 | ✅ 有了（判定逻辑复用 `eval_quality._judge_independent`，只有一份） |
| 一键执行 | ✅ 有了 |
| 前后对比 | ✅ 有了 |
| **多个接入方** | ❌ 只有这一个项目 |
| **CI / 提交前自动卡合入** | ❌ 手动跑，`--max-drop` 只是留了接口 |
| **测试集扩充的审核流程** | ❌ 谁都能改，改了升版本号靠自觉 |

**判断标准很简单：现在只有我一个人在用，那就还不是中台。**
