# 系统性能监控与资源占用分析

> 本文档面向公司内部 IT 运维及开发人员，提供 Linux 服务器环境下系统级性能监控、资源瓶颈识别与常见报错归因的标准化操作指南。

---

## 一、核心监控指标与工具链

| 指标类别       | 关键指标                  | 推荐工具             | 数据采集频率 | 备注                                  |
|----------------|---------------------------|----------------------|--------------|---------------------------------------|
| CPU            | `us`（用户态）、`sy`（内核态）、`wa`（I/O等待）、`id`（空闲） | `top` / `htop` / `mpstat -P ALL 1` | 实时/每秒    | `wa > 20%` 且 `id < 20%` 常指示磁盘瓶颈 |
| 内存           | `used`、`available`、`buff/cache`、`si/so`（swap in/out） | `free -h` / `vmstat 1` | 每秒         | `available < 5%` + `si > 0` 表示内存严重不足 |
| 磁盘 I/O       | `r/s`, `w/s`, `rkB/s`, `wkB/s`, `%util`, `await` | `iostat -x 1`        | 每秒         | `%util > 95%` 或 `await > 50ms` 需关注 |
| 网络           | `rxkB/s`, `txkB/s`, `errs`, `drop` | `sar -n DEV 1` / `iftop` | 每秒         | `drop > 100/s` 可能存在驱动或缓冲区问题 |
| 进程级资源     | CPU%、MEM%、VSZ/RSS、`STATE`（R/S/D/Z）、`%CPU`累计值 | `ps aux --sort=-%cpu` / `pidstat -ru 1` | 每秒         | `STATE = D` 表示不可中断睡眠（常为磁盘/锁等待） |

## 二、典型资源瓶颈识别流程（有序步骤）

1. **确认告警或用户反馈现象**  
   - 明确时间点、受影响服务（如：API 响应超时 > 5s）、是否全局性（单机 or 多节点）。

2. **快速全局概览（<30秒）**  
   ```bash
   uptime              # 查看 load average（重点关注 15min 值）
   free -h             # 观察 available 内存是否低于阈值（建议 ≥10% 总内存）
   iostat -x 1 3       # 连续3次采样，观察 %util 和 await 趋势
   sar -n DEV 1 3      # 检查网卡收发与丢包
   ```

3. **定位高负载进程**  
   - 执行：`pidstat -ru 1 5 | sort -k8nr | head -10`  
     → 按 `%CPU` 降序列出前10个进程（第8列为 `%CPU`）  
   - 若发现 `java`/`python` 进程持续占满单核：结合 `jstack <pid>` 或 `py-spy record -p <pid>` 分析线程栈。

4. **检查内核级阻塞与OOM事件**  
   - 查看 OOM Killer 日志：  
     ```bash
     dmesg -T | grep -i "killed process" | tail -5
     ```
   - 检查是否触发 swap：  
     ```bash
     vmstat 1 5 | awk 'NR==3 {print "swap-in:", $6, "swap-out:", $7}'
     ```

5. **验证配置与限制**  
   - 检查进程级资源限制：`cat /proc/<pid>/limits`  
     → 特别关注 `Max open files`（常导致 `Too many open files` 错误）  
   - 检查系统级参数：  
     ```bash
     sysctl vm.swappiness    # 建议生产环境设为 1~10
     sysctl net.core.somaxconn  # 连接队列长度，避免 `Connection refused`
     ```

## 三、常见报错与资源关联分析

| 报错信息（日志片段）                     | 关联资源瓶颈         | 排查指令示例                          | 解决方向                              |
|------------------------------------------|----------------------|-----------------------------------------|---------------------------------------|
| `java.io.IOException: Too many open files` | 文件描述符耗尽       | `lsof -p <pid> \| wc -l`；`cat /proc/sys/fs/file-nr` | 增加 `ulimit -n`；检查代码未关闭句柄 |
| `Connection refused` / `Cannot assign requested address` | 端口耗尽或连接队列满 | `ss -s`；`netstat -s \| grep -i "listen overflows"` | 调大 `net.core.somaxconn`、`net.ipv4.ip_local_port_range` |
| `No space left on device`（但 `df -h` 显示有空间） | inode 耗尽           | `df -i`；`find /var/log -xdev -type f \| wc -l` | 清理小文件（如旧日志）、调整日志轮转策略 |
| `Killed process <name> (pid <n>)`（dmesg 输出） | 内存不足触发 OOM Killer | `dmesg -T \| tail -20`；`cat /proc/meminfo \| grep -E "(MemFree|MemAvailable|SwapTotal|SwapFree)"` | 优化应用内存使用；增加物理内存；禁用 swap（谨慎） |

## 四、附录：推荐长期监控方案

- **轻量级部署**：`Prometheus + Node Exporter + Grafana`（采集指标全、可视化强、支持告警）  
- **日志关联分析**：ELK Stack（Elasticsearch + Logstash + Kibana）集成 `journalctl -u <service>` 实时日志流  
- **自动化巡检脚本**：定期执行 `check_system_health.sh`（含内存/磁盘/IO/进程数阈值校验，输出 `WARN`/`CRITICAL` 级别摘要）

> ✅ **最佳实践提示**：所有监控需建立基线（Baseline）。建议在业务低峰期连续采集 7 天，生成各指标 P95 值作为动态阈值依据，避免静态阈值误报。
