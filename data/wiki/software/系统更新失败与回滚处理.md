# 系统更新失败与回滚处理

## 概述  
当公司核心业务系统（如 ERP、CRM 或自研微服务集群）执行版本更新时，可能因依赖冲突、配置错误、资源不足或网络中断等原因导致更新失败。本指南提供标准化的故障识别、应急响应、原因定位及安全回滚操作流程，确保系统可用性与数据一致性。

---

## 常见更新失败现象与错误码

| 错误码 | 表现现象 | 可能原因 |
|--------|----------|----------|
| `UPDATE_ERR_102` | 更新脚本中途退出，数据库表结构未完全迁移 | SQL 脚本语法错误 / 权限不足 / 行锁超时 |
| `UPDATE_ERR_205` | 服务启动失败，日志显示 `ClassNotFoundException` | 新版本 JAR 包缺失或类路径污染 |
| `UPDATE_ERR_301` | Kubernetes Pod 处于 `CrashLoopBackOff` 状态 | 配置文件格式错误（如 YAML 缩进异常）、环境变量未注入 |
| `UPDATE_ERR_404` | 前端静态资源加载 404，控制台报 `Failed to load module` | 构建产物未正确部署至 Nginx/CDN，或版本哈希不匹配 |

> ⚠️ 注意：所有错误均需在 **15 分钟内** 完成初步定级（P1-P4），P1（全站不可用）须立即触发回滚流程。

---

## 回滚操作标准流程（以容器化部署为例）

### ✅ 前置检查（执行前必做）
1. 确认当前生产环境已启用 **蓝绿发布策略** 或 **滚动更新保留旧副本**（K8s `revisionHistoryLimit ≥ 3`）；
2. 验证备份完整性：
   - 数据库逻辑备份（`mysqldump` / `pg_dump` 时间戳 ≤ 30 分钟）；
   - 配置中心（如 Apollo/Nacos）历史版本可追溯；
   - 容器镜像仓库中存在上一稳定版本标签（如 `v2.3.7-prod`）；
3. 通知相关方（开发、测试、运维值班群），暂停灰度发布及新任务提交。

### 🔁 手动回滚步骤（Kubernetes 环境）

1. **停止新版本滚动更新**  
   ```bash
   kubectl rollout pause deployment/my-app -n prod
   ```

2. **查看历史发布版本**  
   ```bash
   kubectl rollout history deployment/my-app -n prod
   # 输出示例：
   # REVISION  CHANGE-CAUSE
   # 5         kubectl set image ... v2.4.0-prod
   # 4         kubectl set image ... v2.3.7-prod ← 目标回滚版本
   ```

3. **回退至指定版本（REVISION=4）**  
   ```bash
   kubectl rollout undo deployment/my-app --to-revision=4 -n prod
   ```

4. **验证服务状态**  
   ```bash
   kubectl get pods -n prod -l app=my-app --watch  # 等待全部 READY
   kubectl logs deploy/my-app -n prod --tail=50     # 检查启动日志无 ERROR
   curl -I https://api.company.com/healthz          # HTTP 200 OK
   ```

5. **同步配置与数据校验**  
   - 若更新涉及数据库变更（如新增字段），需执行逆向 SQL（如 `ALTER TABLE DROP COLUMN`）——**仅限幂等操作，且必须在维护窗口内由 DBA 执行**；  
   - 对比关键业务指标（订单创建成功率、API P95 延迟）是否恢复至更新前基线（参考监控平台 Grafana 近 2 小时看板）。

---

## 回滚后必做事项

- 【2 小时内】提交《更新失败根因分析报告》（RCA），明确：
  - 失败环节（CI/CD 流水线哪一阶段？部署？配置？启动？）
  - 根本原因（如：`application-prod.yml` 中 Redis 密码字段被误删）
  - 改进项（例：在 Helm Chart 中增加 `schema-validation` 钩子校验 YAML 合法性）
- 【24 小时内】完成 CI/CD 流水线增强：
  - 新增「预发布环境冒烟测试」关卡（覆盖核心链路 + 配置加载验证）；
  - 在部署脚本中嵌入 `health-check.sh`，失败自动终止并告警。
- 【72 小时内】组织复盘会议，更新《系统发布检查清单》并归档至 Wiki。

## 附录：快速诊断命令速查表

| 场景 | 命令 |
|------|------|
| 查看最近 10 条部署事件 | `kubectl get events -n prod --sort-by=.lastTimestamp | tail -10` |
| 检查 ConfigMap 是否生效 | `kubectl get cm my-app-config -n prod -o yaml \| grep -A5 "database.url"` |
| 容器内验证配置加载 | `kubectl exec -it <pod-name> -n prod -- cat /app/config/application.yml` |
| 回滚后清理无效镜像（可选） | `kubectl set image deploy/my-app *="registry.company.com/app:v2.4.0-prod" -n prod`（覆盖为旧版） |

> 📌 提示：所有操作须通过 **堡垒机审计终端** 执行，并留存完整命令日志（含时间戳与操作人）。
