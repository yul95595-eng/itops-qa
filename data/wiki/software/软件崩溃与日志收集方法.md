# 软件崩溃与日志收集方法

> **适用对象**：IT 运维工程师、开发支持人员、一线技术支持  
> **更新时间**：2024-06-15  
> **知识域**：软件与报错  

---

## 一、常见崩溃现象识别

软件崩溃（Crash）指程序因未捕获异常、内存访问违规、资源耗尽等原因意外终止运行。典型表现包括：

- 程序窗口无响应后自动关闭  
- 控制台输出 `Segmentation fault (core dumped)`、`java.lang.OutOfMemoryError`、`Access violation` 等错误  
- Windows 系统弹出「已停止工作」对话框（含错误代码如 `0x80000003`、`0xC0000005`）  
- Linux 下进程消失且无正常退出码（`echo $?` 返回非 `0` 值，如 `139` 表示 SIGSEGV）

---

## 二、日志收集核心原则

| 原则 | 说明 |
|------|------|
| **时效性** | 崩溃发生后立即收集，避免日志轮转覆盖或缓存清空 |
| **完整性** | 同时采集应用日志、系统日志、核心转储（core dump）、进程快照 |
| **上下文关联** | 记录崩溃时间、用户操作路径、环境版本（OS/Java/.NET/Python 运行时）、配置变更记录 |
| **最小隐私暴露** | 脱敏处理日志中的敏感字段（如密码、手机号、token），使用 `***` 或哈希替代 |

## 三、分平台日志收集方法

### 3.1 Linux 环境

#### ✅ 必收日志项
- 应用标准输出/错误重定向日志（如 `/var/log/myapp/app.log`）
- `journalctl` 系统日志（按服务名过滤）：
  ```bash
  journalctl -u myapp.service --since "2024-06-15 10:00:00" --no-pager
  ```
- Core dump 文件（需提前启用）：
  ```bash
  # 检查是否启用
  cat /proc/sys/kernel/core_pattern
  # 临时启用（root）
  echo "/var/core/core.%e.%p.%t" > /proc/sys/kernel/core_pattern
  sysctl -w kernel.core_pattern=/var/core/core.%e.%p.%t
  ```

#### 🔧 调试辅助命令
```bash
# 查看崩溃进程最后堆栈（需有 debuginfo 包）
gdb /path/to/binary /var/core/core.myapp.12345.1718432100
(gdb) bt full

# 检查内存/句柄限制
ulimit -a
cat /proc/<PID>/status | grep -E "(VmSize|Threads|SigQ)"
```

---

### 3.2 Windows 环境

#### ✅ 必收日志项
- Windows 事件查看器 → 「Windows 日志 → 应用程序」中对应事件（事件 ID：`1000` 应用程序错误、`1001` 错误报告）
- 应用自身日志（检查配置文件中 `log4j2.xml` / `NLog.config` 的 `<target>` 路径）
- 用户模式转储（User-mode dump）：
  - 使用 **ProcDump**（Sysinternals 工具）：
    ```cmd
    procdump64.exe -e -ma -x C:\dumps\ myapp.exe
    ```
  - 或通过任务管理器 → 右键进程 → 「创建转储文件」

#### 🔧 关键注册表设置（启用详细错误报告）
```
HKEY_LOCAL_MACHINE\SOFTWARE\Microsoft\Windows\Windows Error Reporting\LocalDumps
→ DumpFolder = "C:\dumps"
→ DumpCount = 10
→ DumpType = 2 (full memory dump)
```

---

### 3.3 Java 应用专项

除通用日志外，必须收集：

- JVM 启动参数（`ps aux | grep java` 中的 `-Xmx`, `-XX:+HeapDumpOnOutOfMemoryError` 等）
- GC 日志（若启用）：`-Xlog:gc*:file=/var/log/myapp/gc.log:time,uptime,level,tags`
- 内存转储（Heap Dump）：
  - 自动触发：添加 `-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/var/dumps/`
  - 手动触发：`jmap -dump:format=b,file=/var/dumps/heap.hprof <PID>`
- 线程快照：`jstack -l <PID> > /var/log/myapp/thread-dump.txt`

> ⚠️ 注意：`jstack/jmap` 需使用与目标 JVM **相同版本** 的 JDK 工具，否则可能解析失败。

## 四、日志提交与问题初筛流程（运维标准动作）

1. **确认崩溃复现性**  
   - 是否必现？是否与特定输入、时间、负载相关？
2. **提取关键错误标识符**  
   - 异常类名（如 `NullPointerException`）、错误码（`errno=12`）、信号值（`SIGABRT=6`）
3. **比对版本与补丁状态**  
   - 核对软件版本、JVM/.NET Runtime 版本、OS 内核版本（`uname -r` / `winver`）
4. **检查资源瓶颈证据**  
   - 日志中是否有 `java.lang.OutOfMemoryError: Java heap space`、`Too many open files`、`No space left on device`
5. **归档并上传至问题跟踪系统**  
   - 命名规范：`[APP]-[HOST]-[DATE]-[CRASH-TYPE].zip`（例：`billing-srv02-20240615-OOM.zip`）  
   - 必含文件：`error.log`、`thread-dump.txt`、`core.*` 或 `.dmp`、`env-info.txt`（含 `free -h`, `df -h`, `ulimit -a` 输出）

## 五、附录：常见错误码速查表

| 错误码 | 平台 | 含义 | 排查建议 |
|--------|------|------|-----------|
| `SIGSEGV (11)` | Linux | 无效内存访问 | 检查空指针、数组越界、use-after-free |
| `0xC0000005` | Windows | Access Violation | 分析 `.dmp` 中崩溃地址与模块偏移 |
| `java.lang.OutOfMemoryError: Metaspace` | Java | 元空间耗尽 | 增加 `-XX:MaxMetaspaceSize` 或检查类加载泄漏 |
| `Exit code 137` | Linux容器 | OOM Killer 终止 | 检查 `dmesg -T \| grep -i "killed process"` |
| `ERR_CONNECTION_REFUSED`（非崩溃但常伴生） | Web应用 | 后端服务不可达 | 检查依赖服务状态、防火墙、健康检查端点 |
