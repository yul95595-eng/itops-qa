# 磁盘空间不足清理指南

> **适用对象**：公司 IT 运维人员、系统管理员、开发工程师  
> **适用场景**：Linux 服务器（CentOS/RHEL/Ubuntu）磁盘使用率 ≥90%，服务异常或日志报错 `No space left on device`  
> **最后更新**：2024年6月  

---

## 一、快速诊断：定位空间占用大户

### 1. 查看整体磁盘使用情况
```bash
df -hT  # 显示各挂载点文件系统类型与使用率
```
重点关注 `Use%` 列 ≥90% 的分区（如 `/`、`/var`、`/home`）。

### 2. 定位大目录（以根分区为例）
```bash
# 进入高占用分区后执行（如 /var）
cd /var
du -sh * | sort -hr | head -10
```
> ✅ **提示**：`du -sh` 统计目录总大小，`sort -hr` 按人类可读格式逆序排序。

### 3. 查找大文件（含隐藏文件）
```bash
find /var -xdev -type f -size +100M -ls 2>/dev/null | sort -k7,7nr | head -20
```
- `-xdev`：不跨文件系统扫描  
- `-size +100M`：筛选大于100MB的文件  
- `2>/dev/null`：忽略权限拒绝错误

## 二、常见空间占用源及清理方案

| 占用源              | 典型路径                     | 安全清理方式                                                                 | 风险提示                     |
|---------------------|------------------------------|------------------------------------------------------------------------------|------------------------------|
| 系统日志            | `/var/log/`                  | `journalctl --disk-usage` → 清理旧日志：<br>`journalctl --vacuum-size=500M` | 不要直接 `rm *.log`，应使用 `logrotate` 或 `journalctl` |
| Docker 未清理资源   | `/var/lib/docker/`           | `docker system prune -a -f --volumes`（慎用！先确认无重要容器）               | 会删除所有停止容器、镜像、卷  |
| Nginx/Apache 临时文件 | `/var/log/nginx/`, `/var/cache/nginx/` | `rm -f /var/log/nginx/*.gz /var/cache/nginx/proxy/*`                         | 确保服务已重载或重启          |
| Jenkins 构建历史    | `/var/lib/jenkins/jobs/`     | 在 Jenkins Web 界面 → 项目配置 → “Discard old builds” 设置保留策略             | 避免直接删目录，可能破坏元数据 |
| Core dump 文件      | `/var/lib/systemd/coredump/` | `coredumpctl list \| wc -l` → 清理：<br>`systemd-coredump --clean --max-use=2G` | 需 root 权限；调试时慎清       |

## 三、应急释放空间操作步骤（按优先级）

### ✅ 步骤 1：清理 systemd journal 日志（推荐首选）
```bash
# 查看当前日志占用
journalctl --disk-usage

# 保留最近7天日志（安全阈值）
sudo journalctl --vacuum-time=7d

# 或限制总大小为500MB
sudo journalctl --vacuum-size=500M
```

### ✅ 步骤 2：清理 yum/apt 缓存（CentOS/RHEL 或 Ubuntu）
```bash
# CentOS/RHEL
sudo yum clean all && sudo rm -rf /var/cache/yum

# Ubuntu/Debian
sudo apt clean && sudo apt autoclean
```

### ✅ 步骤 3：检查并清理 `/tmp`（注意：部分服务依赖 tmpfiles）
```bash
# 查看/tmp占用
sudo du -sh /tmp/*

# 安全清理（仅删除7天前的文件，排除正在使用的）
sudo find /tmp -type f -mtime +7 -delete 2>/dev/null
# 或使用 systemd-tmpfiles（推荐）
sudo systemd-tmpfiles --clean
```

### ⚠️ 步骤 4：清理 Docker（需确认环境）
```bash
# 查看磁盘占用详情
docker system df -v

# 清理悬空镜像、容器、网络、构建缓存（不删卷）
docker system prune -f

# 清理卷（⚠️ 卷中数据将永久丢失！）
docker volume prune -f
```

## 四、预防措施：避免重复发生

| 措施                          | 实施方式                                                                 |
|-------------------------------|--------------------------------------------------------------------------|
| **启用 logrotate 自动轮转**   | 检查 `/etc/logrotate.d/` 下服务配置，确保 `rotate` 和 `maxsize` 合理（如 `maxsize 100M`） |
| **设置磁盘告警阈值**          | 在 Zabbix/Prometheus 中配置 `df_used_percent{mountpoint="/"} > 85` 告警     |
| **定期巡检脚本（建议 cron）** | `0 2 * * * /usr/local/bin/disk-clean.sh >> /var/log/disk-clean.log 2>&1` |
| **限制 core dump 大小**       | 编辑 `/etc/security/limits.conf`：<br>`* soft core 0`（禁用）或 `* soft core 100000`（限100MB） |

## 五、附录：关键错误码与含义

| 错误信息                                | 常见原因                                  | 关联路径示例                |
|-----------------------------------------|-------------------------------------------|-----------------------------|
| `No space left on device`               | inode 耗尽 或 block 耗尽（需分别排查）     | `/var/spool/postfix/maildrop`（大量小文件） |
| `Cannot write to /var/log/messages`       | `/var/log` 所在分区满，且无可用 inodes     | `df -i` 查看 inode 使用率     |
| `Failed to start docker.service`         | `/var/lib/docker` 分区满导致 daemon 启动失败 | `/var/lib/docker/overlay2/`   |
| `rsync: write failed: No space left on device` | 目标端磁盘满，但 rsync 未及时退出           | 备份任务目标路径              |

> 🔍 **inode 检查命令**：  
> `df -i` —— 查看 inode 使用率；若 `IUse%` ≥95%，需清理大量小文件（如临时缓存、邮件队列、session 文件）。
