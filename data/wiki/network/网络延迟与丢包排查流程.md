# 网络延迟与丢包排查流程

> **适用对象**：IT 运维工程师、网络管理员、SRE  
> **更新时间**：2024年6月  
> **所属知识域**：网络与VPN  

---

## 一、概述

本流程用于系统化定位和解决公司内部用户访问云服务、SaaS 应用或跨地域办公（如通过企业 VPN）时出现的**高延迟（>100ms）** 或 **持续性丢包（≥5%）** 问题。排查遵循「由近及远、分层验证」原则，覆盖终端→局域网→ISP→骨干网→目标服务全链路。

---

## 二、前置检查项（快速过滤常见误报）

在深入诊断前，请确认以下基础状态：

| 检查项 | 方法 | 合格标准 | 常见风险 |
|--------|------|-----------|-----------|
| 终端网络模式 | `ipconfig`（Windows）/ `ifconfig`（Linux/macOS） | 使用有线连接（非Wi-Fi热点）；无双网卡冲突 | Wi-Fi干扰、USB网卡驱动异常 |
| 防火墙/安全软件 | 临时禁用 Windows Defender 防火墙、第三方杀软 | 排除策略拦截ICMP/UDP探测 | 某些EDR产品默认拦截 `tracert`/`mtr` |
| 时间同步 | `w32tm /query /status`（Windows）或 `timedatectl status`（Linux） | 本地时间偏差 ≤ 2s | NTP异常可能导致TLS握手失败，误判为网络问题 |
| DNS解析稳定性 | `nslookup example.com 8.8.8.8` ×3次 | 解析响应时间 < 100ms，结果一致 | 本地DNS缓存污染或上游DNS故障 |

✅ 所有前置项通过后，进入正式排查流程。

---

## 三、标准化排查步骤

### 步骤1：确认现象并建立基线

- 使用标准测试目标（推荐）：
  - 公共基准：`8.8.8.8`（Google DNS）、`1.1.1.1`（Cloudflare）
  - 业务目标：`app.company.com`（需明确IP及端口，如 `443/tcp`）
- 执行三次基线测试（间隔2分钟），记录：
  ```bash
  ping -c 20 8.8.8.8          # 观察丢包率 & avg RTT
  mtr --report-wide -c 20 8.8.8.8  # 生成路由级延迟/丢包分布
  ```

> ⚠️ 注意：避免使用 `ping` 测试 HTTPS 服务——部分CDN/防火墙会限速ICMP但放行TCP。关键业务请改用 `tcpping` 或 `curl -w "@format.txt" -o /dev/null -s https://app.company.com`

---

### 步骤2：分段路径分析（核心）

按 OSI 模型自下而上逐层验证：

| 层级 | 工具与命令 | 关键指标 | 异常判定 |
|------|-------------|------------|-------------|
| **L1/L2（物理与数据链路）** | `ethtool eth0`（Linux）、`netsh int ip show interfaces`（Win） | Speed: `1000Mb/s`，Duplex: `Full`，Errors: `0` | `rx/tx errors > 0` → 网线/交换机端口故障 |
| **L3（网络层）** | `tracert 8.8.8.8`（Win） / `traceroute 8.8.8.8`（Linux） | 查看跳数、每跳延迟突增点（ΔRTT > 50ms）、星号 `*` 连续出现 | 第3跳起持续 `*` → 中间设备禁ICMP或ACL限制 |
| **L4（传输层）** | `tcpping -x 20 app.company.com 443` | TCP SYN 延迟 & 连接成功率 | 成功率 < 95% 或 SYN-RTT > 300ms → 目标端口拥塞/防火墙拦截 |
| **L7（应用层）** | `curl -v --connect-timeout 10 -o /dev/null https://app.company.com` | TLS握手时间、HTTP状态码、首字节时间（TTFB） | `SSL connect timeout` → 证书/中间设备拦截；`HTTP 503` → 后端过载 |

---

### 步骤3：VPN专项检查（若使用企业SSL/IPsec VPN）

| 场景 | 检查方法 | 说明 |
|------|-----------|------|
| **VPN隧道连通性** | `ping` 隧道内网网关（如 `10.100.1.1`） | 隧道未建立则检查客户端日志（如 Cisco AnyConnect `AnyConnect Diagnostics`） |
| **MTU协商异常** | `ping -f -l 1472 x.x.x.x`（Windows）<br>`ping -M do -s 1472 x.x.x.x`（Linux） | 若 `1472` 失败但 `1400` 成功 → MTU不匹配导致分片丢包（常见于PPPoe/VPN叠加场景） |
| **DNS泄漏** | 访问 [https://dnsleaktest.com](https://dnsleaktest.com) | 确认解析请求全部经VPN DNS（如 `10.100.2.10`），而非本地ISP DNS |

> 🔍 **典型VPN错误码参考**：  
> - `Error 412`（AnyConnect）→ 客户端时间偏差 > 2min  
> - `Phase 2 SA not established`（IPsec）→ 加密算法不匹配（如 IKEv2 提议中 AES-GCM vs AES-CBC）  
> - `TLS handshake timeout` → VPN网关证书过期或 OCSP 响应不可达

## 四、常见根因与对应措施

| 现象 | 最可能根因 | 应对措施 |
|------|--------------|------------|
| 本地LAN内高延迟（仅WiFi） | 信道干扰 / 802.11n/ac兼容性问题 | 切换至5GHz频段；关闭WMM节能模式；更换无线信道 |
| `tracert` 中某跳延迟突增且后续跳正常 | 该节点QoS限速或CPU过载（非故障） | 联系ISP提供该节点负载报告；尝试不同时间段复测 |
| 仅访问特定SaaS丢包（如 Salesforce） | 目标CDN节点区域性故障或BGP路由异常 | 查询 [https://status.salesforce.com](https://status.salesforce.com)；使用 `bgp.he.net` 查看AS路径变化 |
| VPN连接后所有外网丢包 | 客户端分流策略错误（Split Tunneling 关闭） | 在VPN配置中启用 `Split Tunneling`，仅路由公司内网流量经隧道 |

## 五、附录：关键命令速查表

```markdown
# Linux/macOS
mtr --report-wide -c 20 target.com      # 路由级诊断（需安装 mtr）
tcpping -x 10 target.com 443           # TCP端口连通性
ss -tuln | grep :443                   # 本地端口监听检查

# Windows
pathping -n -q 1 -h 15 target.com      # 结合ping+tracert的增强版
netsh interface ipv4 show subinterfaces  # 查看各接口MTU设置
```
