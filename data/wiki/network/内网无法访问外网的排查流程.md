# 内网无法访问外网的排查流程

> **适用范围**：公司内部办公网络（含有线/无线终端）、DMZ区服务器、远程接入VPN用户  
> **前置条件**：已确认终端IP地址获取正常（DHCP或静态配置有效），且能ping通内网网关  

---

## 一、快速定位层级（分层排查法）

采用 OSI 模型自下而上逐层验证，避免盲目操作：

| 层级 | 关键检查项 | 验证命令/方法 | 常见异常现象 |
|------|-------------|----------------|----------------|
| **物理层 & 数据链路层** | 网线/光模块状态、交换机端口UP/DOWN、VLAN配置 | `ethtool eth0`（Linux）<br>`ipconfig /all`（Windows）查看“媒体状态” | Link down、双工不匹配、VLAN ID 错误（如终端在 VLAN 10，但接入端口配置为 VLAN 20） |
| **网络层** | 默认网关可达性、路由表、ARP缓存 | `ping <网关IP>`<br>`ip route show`（Linux）<br>`route print`（Windows）<br>`arp -a` | 网关不可达、默认路由缺失、ARP表中网关MAC为空或异常 |
| **传输层** | 出口NAT/防火墙策略、TCP连接能力 | `telnet <公网DNS IP> 53`（测试UDP/DNS常需额外验证）<br>`curl -v http://www.baidu.com`（观察HTTP响应头） | 连接超时（Connection timed out）→ 可能被ACL/NAT阻断；拒绝连接（Connection refused）→ 目标端口未开放或代理拦截 |
| **应用层** | DNS解析、代理设置、HTTPS证书信任链 | `nslookup www.baidu.com`<br>`cat /etc/resolv.conf`（Linux）<br>`netsh winhttp show proxy`（Windows） | `server can't find xxx: NXDOMAIN` → DNS故障<br>`*** can't find xxx: server failed` → DNS服务器无响应 |

## 二、重点场景专项排查步骤

### 2.1 终端可通网关但无法解析域名（DNS故障）

1. 执行 `nslookup www.baidu.com 114.114.114.114`（直连公共DNS）  
   - ✅ 成功 → 说明本地DNS服务器（如公司内部DNS）异常  
   - ❌ 失败 → 检查出口防火墙是否放行UDP 53（DNS查询）及TCP 53（区域传输/大响应）  
2. 查看 `/etc/resolv.conf`（Linux）或网络适配器DNS设置（Windows）  
   - 确认未被恶意篡改（如指向非法DNS）  
   - 若使用公司内网DNS（如 `10.10.1.10`），尝试 `dig @10.10.1.10 www.baidu.com +short`  
3. 检查DNS服务器自身连通性与服务状态：  
   - `ping 10.10.1.10`  
   - `nc -zv 10.10.1.10 53`  
   - 登录DNS服务器，执行 `systemctl status named`（BIND）或 `service dns-server status`（Windows Server）

### 2.2 终端可解析域名但无法建立HTTP/HTTPS连接

1. 使用 `curl -I http://www.baidu.com --connect-timeout 5` 测试基础HTTP连通性  
   - 返回 `HTTP/1.1 200 OK` → 应用层通，问题可能在浏览器或安全策略  
   - 返回 `Failed to connect` → 检查出口防火墙策略、NAT映射、SSL解密设备拦截  
2. 针对HTTPS，追加证书验证：  
   ```bash
   curl -v https://www.baidu.com 2>&1 | grep -E "(Connected|subject|issuer)"
   ```  
   - 若出现 `SSL certificate problem: unable to get local issuer certificate` → 本地CA证书库缺失（常见于Linux容器/精简系统）  
   - 若卡在 `TLS handshake` → 中间设备（如SSL Inspection Proxy）证书未被终端信任  
3. 检查系统代理设置：  
   - Linux：检查 `http_proxy`/`https_proxy` 环境变量及 `~/.curlrc`  
   - Windows：`设置 > 网络和Internet > 代理`，确认「自动检测设置」或「使用设置脚本」未启用错误PAC文件  

### 2.3 VPN用户无法访问外网（Split Tunneling 或 Full Tunnel 场景）

| 模式 | 典型表现 | 排查要点 |
|------|-----------|------------|
| **Split Tunneling（分流隧道）** | 内网资源可访问，公网网站部分可打开（如HTTP可，HTTPS不可） | 检查客户端路由表：<br>`ip route list table all \| grep "via"`<br>确认公网流量是否被错误导向VPN网关（应直出） |
| **Full Tunnel（全隧道）** | 所有流量经VPN出口，但外网完全不可达 | 1. 登录VPN网关后台，检查：① 上行链路（WAN口）是否UP；② NAT规则是否启用；③ 出口ACL是否放行 `0.0.0.0/0` 的HTTP/HTTPS/DNS<br>2. 在VPN网关执行 `tcpdump -i wan0 port 53` 观察DNS请求是否发出并收到响应 |

## 三、常见错误码速查表

| 错误信息 | 含义 | 排查方向 |
|----------|------|-----------|
| `Destination Host Unreachable` | 路由不可达（三层无路径） | 检查网关路由表、核心交换机静态路由/OSPF/BGP状态 |
| `Request timed out`（ping网关成功，ping公网IP失败） | 出口防火墙丢包、NAT未生效、ISP链路中断 | 抓包定位丢包点（内网→网关→防火墙→出口路由器） |
| `No route to host`（telnet失败） | 目标端口被防火墙DROP（非REJECT），或目标主机关闭该服务 | 使用 `nmap -sS <IP> -p 53,80,443` 辅助判断策略类型 |
| `ERR_CONNECTION_REFUSED`（Chrome） | 本地代理转发失败、HTTPS拦截设备未正确处理SNI | 关闭浏览器代理，或检查企业级SSL解密设备证书安装状态 |

## 四、附：关键日志采集命令（管理员权限执行）

```bash
# 1. 实时抓取出口方向DNS与HTTP流量（假设出口接口为ens192）
sudo tcpdump -i ens192 -n -w /tmp/egress_debug.pcap port 53 or port 80 or port 443

# 2. 查看防火墙实时丢包统计（以iptables为例）
sudo iptables -L FORWARD -nv \| grep -E "(DROP|REJECT)"

# 3. 检查NAT转换状态（Linux netfilter）
sudo conntrack -L \| head -20

# 4. 查询最近1小时系统级网络错误（dmesg环形缓冲区）
dmesg \| grep -i "error\|drop\|ovf" \| tail -15
```
