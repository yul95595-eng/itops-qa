# 办公网带宽占用过高排查指南

> **适用对象**：IT 运维工程师、网络管理员  
> **更新时间**：2024年6月  
> **知识域**：网络与VPN  

---

## 一、现象识别

当办公网出现以下任一情况时，需启动带宽占用过高排查流程：

- 内网访问缓慢（如OA、邮件、内部系统响应超时 >3s）
- 视频会议频繁卡顿、丢帧或自动降清晰度
- 员工集中反馈“上网慢”，但外网测速（如 speedtest.net）显示下行正常
- 防火墙/出口路由器监控界面显示 WAN 口利用率持续 ≥85%（15分钟粒度）

> ⚠️ 注意：单次瞬时峰值（<30秒）不构成问题，需确认是否为**持续性高负载**（连续5分钟以上 ≥80%）。

---

## 二、快速定位工具与方法

### 2.1 出口设备基础检查（路由器/防火墙）

| 检查项 | 操作命令 / 路径 | 关键指标 | 异常表现 |
|--------|----------------|----------|-----------|
| 实时流量TOP 10会话 | `show top talkers`（Cisco ASA）<br>`/usr/bin/nethogs -t`（Linux网关） | 源IP、目的IP、协议、带宽（KB/s） | 单IP长期占用 >5Mbps（千兆出口下） |
| 接口统计 | `show interface GigabitEthernet0/0` | `input rate`, `output rate` | Input/Output bps 接近接口带宽上限（如1Gbps口 >900Mbps） |
| 连接数统计 | `show conn count`（ASA）<br>`ss -s`（Linux） | `total established` > 50,000 | 存在连接数爆炸（可能为扫描、代理滥用或恶意软件） |

### 2.2 常见高带宽行为特征对照表

| 行为类型 | 典型协议/端口 | 流量特征 | 排查线索 |
|----------|----------------|------------|-------------|
| P2P下载（迅雷、qBittorrent） | TCP/UDP 6881–6999, DHT | 大量并发小包、长连接、上行占比高（>40%） | `netstat -an \| findstr :688[1-9]`（Windows） |
| 云盘自动同步（OneDrive/坚果云） | HTTPS (443), WebDAV | 固定周期心跳 + 持续上传流、User-Agent含`OneDrive`/`Jianguoyun` | 抓包过滤 `http.host contains "jgyun"` |
| 视频会议后台上传（Zoom/腾讯会议） | UDP 8801–8810, RTP | 高抖动容忍、UDP流无重传、TTL=64 | `tshark -f "udp portrange 8801-8810" -c 20` |
| VPN隧道异常（SSL-VPN/IPSec） | TCP 443 / UDP 500,4500 | 单用户隧道持续 >100Mbps、无业务交互仍保活 | 查看VPN会话表中`Idle Timeout`字段是否被禁用 |

## 三、分层排查步骤

### 3.1 第一层：确认出口瓶颈（5分钟）

1. 登录核心出口防火墙（如 FortiGate / Palo Alto / 华为USG），进入 **Monitor → Network → Interfaces**  
2. 查看 `wan1`（或对应互联网接口）的 **Real-time Graph**，确认：
   - 当前 `In/Out Rate` 是否 ≥90% 带宽标称值；
   - 是否存在明显单向拥塞（如 Out 峰值高但 In 正常 → 内网主动外发异常）；
3. 若确认出口拥塞，执行 `show system session list | grep -E "(TIME_WAIT|ESTABLISHED)" | wc -l`，若连接数 >80,000，进入第2层；否则跳至第3层。

### 3.2 第二层：定位高流量源IP（10分钟）

1. 在出口设备执行会话TOP分析：
   ```bash
   # FortiGate 示例
   diagnose sys session list | grep -A 5 -B 5 "proto=6\|proto=17" | head -n 50
   ```
2. 提取前5个高流量 `src-ip`，记录其所属部门/办公区域（通过DHCP租约表或AD IP绑定信息）；
3. 对目标IP执行：
   - `arping -c 3 <IP>` 确认在线；
   - `nmap -sT -p 135,445,3389 <IP>` 初步判断是否为Windows终端（开放SMB/RDP）；
   - 如为服务器IP，检查其进程：`top -b -n1 \| head -20`（Linux）或任务管理器网络排序（Windows）。

### 3.3 第三层：终端侧深度验证（15分钟）

对锁定的终端（需远程协助或现场支持）：

1. **Windows 终端**：
   - 打开资源监视器（`resmon.exe`）→ “网络”选项卡 → 按“发送/接收 B/sec”排序；
   - 运行命令：  
     ```powershell
     Get-NetTCPConnection | Where-Object {$_.State -eq "Established"} | 
       ForEach-Object {
         $proc = Get-Process -Id $_.OwningProcess -ErrorAction SilentlyContinue
         [PSCustomObject]@{
           LocalAddress = $_.LocalAddress
           RemoteAddress = $_.RemoteAddress
           ProcessName = $proc.ProcessName
           SentBytes = $proc.NetIOBytesSent
         }
       } | Sort-Object SentBytes -Descending | Select-Object -First 5
     ```

2. **macOS/Linux 终端**：
   ```bash
   sudo lsof -i -P -n | grep -E "(ESTABLISHED|CONNECTED)" | awk '{print $1,$9,$10}' | sort | uniq -c | sort -nr | head -10
   ```

3. **关键判定**：
   - 若发现 `WeChat.exe`、`TencentMeeting.app`、`Chrome` 等进程持续上传 >2Mbps，检查其后台活动（如微信自动备份相册、会议录制到云端）；
   - 若出现 `python`, `curl`, `wget` 等非办公进程高频外连，需进一步检查定时任务（`crontab -l`, `launchctl list`）。

## 四、典型误判与规避建议

| 误判场景 | 正确归因 | 应对措施 |
|----------|-----------|-----------|
| 防火墙CPU使用率高 → 误判为带宽问题 | 实际为IPS策略全开导致软转发瓶颈（CPU 95%但接口利用率仅40%） | 检查 `diagnose hardware deviceinfo nic` 中 `rx/tx queues` 是否堆积；临时关闭深度检测策略验证 |
| 员工报“视频卡” → 直接扩容带宽 | 实际为WIFI信道干扰（2.4G频段同频AP过多） | 使用 `WiFi Analyzer`（Android）或 `Apple Wireless Diagnostics`（Mac）扫描信道重叠率 |
| SSL-VPN用户带宽突增 → 认定为个人滥用 | 实际为公司统一部署的终端安全软件（如CrowdStrike）触发全盘扫描上传IOC日志 | 查看终端进程名 `FalconSensor` 或 `csagent`，确认是否在执行 `sensor update` 或 `full scan` |

## 五、附录：常用命令速查

| 场景 | 命令（Linux网关） | 说明 |
|------|------------------|------|
| 实时流量TOP 5进程 | `sudo nethogs -t -c 5` | `-t`: 显示时间戳；`-c 5`: 采集5次后退出 |
| 统计各IP总流量（最近1小时） | `sudo tcpdump -i eth0 -w /tmp/traffic.pcap & sleep 3600; sudo killall tcpdump; tshark -r /tmp/traffic.pcap -T fields -e ip.src -e frame.len \| awk '{a[$1]+=$2} END{for (i in a) print i,a[i]}' \| sort -k2 -nr \| head -5` | 需提前安装 `tshark` |
| 检查是否存在UDP泛洪 | `watch -n1 'ss -u \| wc -l'` | 持续观察UDP socket数是否异常增长（>5000） |
